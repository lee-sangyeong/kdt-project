Business Problem
모터 베어링 고장은 라인 정지 비용으로 이어진다
프레스 구동부와 생산 설비 모터의 베어링 이상은 갑작스러운 정지, 품질 불안정, 긴급 정비 비용으로 연결됩니다. 단순 온도 임계값이나 순간 진동값만으로는 조기 이상을 설명하기 어렵기 때문에, 진동 신호와 시간 추세를 함께 보는 구조가 필요했습니다.
Project Scope
센서 수집부터 작업자 화면까지 연결
로컬 실제 시연용 폴더 기준으로 STM32 펌웨어, Raspberry Pi 추론 코드, FastAPI/WebSocket 대시보드, Arduino 경보, XJTU RUL 모듈, PUBLIC_BEARING_100 결함 후보 진단 모듈이 포함되어 있습니다. 발표자료 파일은 별도로 존재하지 않았습니다.
정리 기준: 이 페이지는 팀 역할 분담을 따로 나누지 않고, 이상영 포트폴리오용으로 실제 로컬 패키지에서 확인한 전체 구현 과정과 산출물을 근거 중심으로 정리했습니다.

03

핵심 코드와 구현 포인트

Communication
고정 길이 UART 패킷과 CRC 검증
진동 데이터는 한 바이트만 밀려도 X/Y/Z 축 배열이 깨지기 쉽습니다. 그래서 STM32는 2409바이트 고정 패킷으로 400개 샘플을 보내고, Raspberry Pi는 payload 길이, 채널 수, 샘플 수, CRC를 모두 검증한 뒤 추론에 투입합니다.
Inference
PyTorch 없는 엣지 추론 구조
학습은 PyTorch 기반으로 수행하되 실제 추론은 saved_models/cnn_ae_dc775.onnx를 ONNX Runtime으로 실행합니다. Raspberry Pi에서 불필요한 학습 프레임워크 의존성을 줄이는 배포 관점의 설계입니다.
Alert Logic
재구성 오차와 Hysteresis 경보
1D CNN AutoEncoder의 입력-복원 MSE를 이상 스코어로 계산하고, NORMAL/CAUTION/WARNING을 바로 바꾸지 않고 최근 5회 중 3회 이상 조건으로 안정화합니다. 작업자 입장에서 경보 흔들림을 줄이기 위한 로직입니다.
Dashboard
Live, Replay, Scripted Demo 분리
실제 하드웨어 live가 끊겨도 UI 검증과 발표 흐름이 멈추지 않도록 dc775_live, dc775_replay, femto_replay, scripted_demo 모드를 나누었습니다.
구현 관점의 핵심: 모델 하나를 만든 프로젝트가 아니라, 센서 신호 수집, 통신 무결성, 엣지 추론, 경보 출력, 작업자 대시보드를 하나의 운용 흐름으로 연결한 점이 핵심입니다.

06

한계, 개선 방향, 기업 관점의 의미

예지보전 시스템의 품질은 모델 정확도만이 아니라 데이터 수집 안정성, 통신 무결성, 엣지 배포 가능성, 작업자가 신뢰할 수 있는 화면과 경보까지 함께 결정됩니다.
— 아진산업 SILI 예지보전 프로젝트 정리
현재 한계
로컬 패키지에는 logs/thresholds_dc775.json과 data/dc775_test replay 세션이 없었습니다. 따라서 DC775 live 임계값 재현과 replay 검증은 원본 데이터/하드웨어 연결이 추가로 필요합니다.
개선 방향
DC775 run-to-failure 데이터를 장시간 수집해 실제 모터 기준 threshold, RUL, 결함 주파수 설정을 보강해야 합니다. PUBLIC/XJTU 성능은 보조 알고리즘 검증으로 분리해 설명하는 편이 정확합니다.
직무 의미
임베디드, 센서 데이터, AI 추론, 대시보드가 동시에 필요한 제조 자동화 직무에서 “현장 신호를 서비스 가능한 판단으로 바꾸는 흐름”을 이해하고 구현한 경험으로 설명할 수 있습니다.
